# Registrations, players and Mercado Pago payments

Cross-repo feature on branch `feat/registrations` in both repos (from `origin/dev`): frontend `R:\repositories\incoders\zonar-hub` (this file) and API `R:\repositories\incoders\zonar-hub-api`. Completes the real circuit: a player registers a pair on the public tournament page, the organizer approves it, pays through the organization's Mercado Pago, and confirmed pairs feed the draw. Delivered in reviewable slices; PRs to `dev`, promotion and production migrations only with the owner's confirmation.

### Design decisions (parent, binding for workers)

- **D1 Additive schema.** New tables, never rewriting the legacy `registrations` table (one row per user, unused by any endpoint except the dashboard count): `players` (organization_id, optional user_id, first/last name, email, phone, document_id, birth_date, gender_id, category_id, club, is_active; unique (organization_id, lower(email)) when email present, unique (organization_id, document_id) when present), `tournament_registrations` (tournament_id cascade, organization_id, status, source `public|admin`, payment_status, contact_email, notes, public_name_consent, created/updated, revision), `tournament_registration_participants` (registration_id cascade, slot_number, player_id; unique (registration_id, slot_number) and one active registration per player per tournament), `tournament_eligibility_profiles` + slots (organization scoped) and nullable `tournaments.eligibility_profile_id`. The dashboard count moves to the new table. Grants per repo convention (service_role).
- **D2 Statuses.** Registration: `pending` → `confirmed` | `rejected` | `waitlisted`; `waitlisted` → `confirmed` when a place frees; any non-final → `cancelled`. Capacity = `max_pairs` over `confirmed`; confirming beyond capacity is refused; public submissions arrive `pending` (or `waitlisted` when pending+confirmed already reach capacity). Registration window enforced on public submissions (`registration_start_date`..`registration_end_date`). Payment: `not_required` (fee 0/null) | `pending` | `paid` | `refunded` | `failed`.
- **D3 Eligibility.** Server-side validation of each slot (gender, category with the existing level tolerance rule, min/max age from birth date) using the tournament's eligibility profile, else the tournament's own `category_id`/`gender_id`/`modality` (participants per modality: single 1, doubles 2, teams N). The client rules (`EligibilityValidationService`, `RegistrationStrategyService`) become a mirror of the API, one source of truth per side. Missing player data that a rule needs rejects the registration until the player record is completed (L8); an inactive eligibility profile is ignored and the tournament's own rules apply (L8).
- **D4 Public flow (anonymous).** `GET /api/public/tournaments/{slug}/registration` (open/closed, window, capacity left, fee, slots and their rules, consent text key); `POST .../registration/code` sends a 6-digit code to the contact email (registration-scoped, NOT the signup code, rate-limited, 15 min, hashed in cache); `POST .../registration` with participants + code creates or reuses org `players` by email/document (never overwriting existing data with public input beyond filling empty fields), returns a public registration reference and, when a fee applies and the organization is connected, a Mercado Pago checkout URL; `GET .../confirmed-pairs` lists confirmed pairs' display names only for registrations with `public_name_consent`, otherwise "Pareja confirmada" anonymised. No ids of players, no emails/phones in public responses.
- **D5 Admin.** AdminOrAbove + `TournamentOrganizationAccess`: players CRUD with search (organization scoped), eligibility profiles CRUD, tournament registrations list/create/confirm/reject/waitlist/cancel/payment mark (manual `paid`/`refunded` allowed for cash payments), and `GET .../registrations/draw-participants` that maps confirmed registrations to `DrawParticipant` (`id` = registration id, `members` in slot order, `displayName` joined with " / ", `separationKey` = shared club when all members share it else first member's club, `seedRank` empty).
- **D6 Master code.** Moves to configuration `Authentication:DevelopmentMasterCode` (env `Authentication__DevelopmentMasterCode`, L6), honoured only when the environment is Development and the value is non-empty; removed from source and from the frontend wizard.
- **D7 Mercado Pago (pending research L4).** Organization connects via OAuth (authorization code); tokens stored server-side only, encrypted at rest, refreshed before expiry; never returned to clients. Checkout Pro preference per registration in the organization's account with optional `marketplace_fee` from configuration (default 0); `notification_url` webhook verifies the signature, re-reads the payment from the API and updates `payment_status` idempotently; return URLs to the public tournament page. Platform credentials (`MercadoPago__ClientId`, `MercadoPago__ClientSecret`, webhook secret) only from environment. Sandbox test users for verification.
